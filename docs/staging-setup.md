# 테스트 브랜치와 교내 시설 1차

테스트 브랜치: `staging`. 운영 기준: `main` (작업 시작 커밋 7820f91). 운영에는 이번 변경을 병합하거나 배포하지 않는다.

## 이번에 구현한 범위

- `data/campus-registry.json`: 공개 검토된 교내 건물 목록. 기존 학식 건물 4곳과 카카오 장소 검색으로 건물 위치를 확인한 IT1호관 1곳. 강의실/시설/층별 도면/보행로는 실제 검증 자료가 없어 아직 비어 있다.
- `/api/search`: 등록 교내 건물의 별칭을 우선 검색. IT1/IT-1/IT 1호관은 외부 검색 키 없이도 반환된다. 기존 지도·길찾기·시간표 장소 검색이 같은 API를 사용한다. 미확인 306호를 실제 호실 좌표로 반환하지 않는다.
- 검색창 아래 가로 범주 칩, 화면 픽셀 기준 시설 핀 묶음과 숫자, 같은 좌표의 층별 시설 목록, 건물 핀 켜기/끄기, 건물 상세·출발/도착 버튼.
- 도면 기능은 사용자 요청으로 보류했다. 건물 내부 지도 버튼에는 “아직 지원하지 않는 기능입니다”를 표시한다. 도면 업로드·OCR·실내 화살표·층간 경로는 제공하지 않는다.
- `/campus-lab`: 서버가 검증한 전용 관리자 로그인 후 지도 좌표를 직접 찍는 시설/건물 등록·수정·삭제. 입력 중인 양식과 저장 시설은 버전이 있는 localStorage에 보관한다. 같은 사이트·같은 브라우저에서만 공유하며 운영 DB에는 쓰지 않는다. 기기 데이터 삭제에 대비해 JSON 내보내기·불러오기를 제공한다. 기존 v1 초안은 위치 확인이 필요한 상태로 가져온다. 도면 파일 첨부는 제거했다. 관리자 설정 및 main 반영 준비는 [admin-and-release.md](admin-and-release.md)를 따른다.
- 사용자가 좌표 확인에 체크한 시설만 기기 내 검색·분류 핀·길찾기에 연결한다. 공용 카탈로그는 변경하지 않는다. 층·호실은 설명이며 실내 이동 계산이 아니다. 건물로 이름을 대체하지 않고 선택한 시설 이름을 목적지에 보존한다. 새 기기 등록 건물도 건물 핀과 건물 선택에 사용할 수 있다.
- 메인 검색은 교내를 기본으로 하고 전체 검색으로 전환할 수 있다. 교외 출발지는 기존 길찾기 검색에서 계속 사용한다. 분류 선택과 핀 표시를 연결하고 시설/건물의 가까운 핀은 픽셀 거리로 묶는다. 같은 좌표 시설은 목록에서 고른다.
- 테스트 환경 배너·검색 노출 방지, 정확한 허용 출처 추가 설정, 운영 DB 연결 차단.

## Vercel 연결 절차

2026-10-30 연결 완료: `seungmiii` 팀의 별도 프로젝트 `knu-campus-navigation-test` (`prj_BV2a5xKHBUwVOzLOC81zHGppGETj`). 기준 브랜치는 `staging`, Node 24이며 staging 이외 브랜치는 빌드를 건너뛴다. Git 연동으로 staging push 시 자동 배포한다. 고정 주소는 `https://knu-campus-navigation-test.vercel.app`이다. `KNU_ENV=staging`과 해당 주소의 정확한 허용 출처를 모든 환경에 설정했다.

운영 프로젝트·main·운영 DB·인증 설정은 변경하지 않았다. 운영 프로젝트에서도 staging의 Preview가 자동 생성되지만 운영 고정 주소로 승격하지 않는다. 독립 테스트 DB 연결 전까지 테스트의 로그인/시간표 저장은 비활성화된다. 사용자 선택에 따라 시설 초안은 우선 기기에 보관한다.

사용자가 테스트 프로젝트에 `KAKAO_REST_API_KEY`, `DAEGU_BUS_API_KEY`, `KMA_API_KEY`를 추가했고 테스트 Production에 재배포했다. 본 프로젝트의 Production에도 세 키가 있는 것을 값 조회 없이 확인했다. 두 사이트 모두 장소 검색·경북대학교서문건너 정류장 실시간 버스·기상청 날씨·IT1→복지관 도보가 HTTP 200이었다. 동대구역→글로벌플라자 대중교통도 각각 13개 경로를 반환했다. 교내의 짧은 구간에서 대중교통 NO_ROUTE가 나오는 것은 키 누락과 구분한다. 실제 카카오 지도 및 교내 카페·편의점 조회도 확인했다. 운영 키·DB 설정을 복사하거나 변경하지 않았다.

아래는 재설정/후속 준비 절차다.

1. 같은 Git 저장소에 별도 `knu-campus-navigation-test` 프로젝트를 생성하고 **그 프로젝트만** `staging`을 배포 기준으로 지정한다. 기존 운영 프로젝트 설정은 변경하지 않는다.
2. 테스트 프로젝트의 Production/Preview 환경에 `KNU_ENV=staging`을 넣는다. 이 프로젝트의 Production은 테스트 고정 주소를 뜻하며 운영 데이터 사용을 의미하지 않는다.
3. 테스트용 독립 Supabase DB/Auth/Storage가 확보되면 `KNU_TEST_SUPABASE_PROJECT_REF`, `SUPABASE_URL`, publishable key를 맞춰 설정한다. 운영 프로젝트 ref `mezfiokxepbwfdevvjce`는 허용하지 않는다. 별도 테스트 DB가 준비되지 않은 동안 인증/시간표는 비활성화된다. 일반 시설·지도 UI는 사용할 수 있다.
4. 테스트용 외부 API 키를 설정하고 확정된 테스트 도메인을 카카오 JS 허용 도메인, 인증 반환 주소와 `KNU_ALLOWED_ORIGINS`에 등록한다. 운영 비밀키 전체를 무조건 복제하지 않는다. 카카오 설정 전에는 지도 기본 공급자로 전환될 수 있고 교외 카테고리 조회가 제한될 수 있다.
5. 배포 후 실제 브랜치·커밋·고정 주소·페이지 robots·빈 테스트 인증 구성·브라우저 지도·시설 검색을 검증한다. 운영 URL과 혼동되지 않는 배너가 보여야 한다.

## 데이터 공개 절차

공용 카탈로그 추가는 담당자가 이름·건물·층·호실·위치·사용 조건·출처를 검토한 뒤 진행한다. `status=draft`는 서버 공개 검색에 노출하지 않는다. 기기에 저장한 수동 시설은 위치 확인을 마친 경우에만 해당 브라우저의 검색·핀에서 “내 기기”로 표시한다. 내보낸 파일을 다른 사용자에게 공개하거나 DB 등록 완료로 설명하지 않는다.

시설 위치 표시는 보행 경로 검증과 별개다. 실내 시설의 경우 실제 출입구·복도·계단/엘리베이터 연결과 도면상의 문 위치를 확보한 뒤 경로 안내를 구현한다. 숫자 호실만으로 층/문 좌표를 생성하지 않는다.

## 운영 반영

staging에서 검사·현장 확인 → 변경 diff 검토 → 선택한 기능만 main 대상 PR → 운영 환경 검증 후 병합. 테스트 환경 설정 파일을 운영 설정으로 덮어쓰지 않는다. 환경 격리 코드는 main의 Vercel Production 배포에서 기존 인증을 허용하며, 로컬에서 운영 DB를 쓰려면 명시적인 `KNU_ENV=production` 설정이 필요하다.
