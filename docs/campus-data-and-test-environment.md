# 교내 상세 지도 데이터 확보 및 테스트 환경 검토

기준일: 2026-10-30. 아래는 조사·설계 기준이다. 이후 승인된 1차 구현과 테스트 환경의 실제 상태는 [staging-setup.md](staging-setup.md)에 기록한다.

## 결론

요청 UI와 실외→교내→층별 강의실 안내는 단계적으로 구현 가능하다. 가장 큰 준비 과제는 공개·재사용 가능한 층별 도면과 검증된 통행 연결 데이터다. 외부 장소 API 하나로 모든 교내 시설과 실내 경로가 완성되지는 않는다. 공개 자료 + 학교 제공 자료 + 현장 확인 + 관리자 검토형 수동 등록을 함께 사용한다.

## 벤치마킹 확인 범위

[고대로 개발팀의 출시 안내](https://www.koreapas.com/m/view.php?id=freead&no=251490)는 실내 지도, 편의시설, 실내외 길찾기, 건물 별칭 검색을 소개하며 일부 시설·강의실은 입력 중이라고 설명한다. [App Store 소개](https://apps.apple.com/kr/app/고대로/id6740149875)도 실내 구조·편의시설 안내를 설명한다. 이번 조사는 공개 소개 자료 기준이며 앱을 설치해 전체 상호작용을 직접 검증한 것은 아니다. 고대로의 데이터 확보 경위·학교 도면 제공 계약·재사용 가능한 공개 API는 확인하지 못했다. UI를 참고하는 것과 해당 서비스의 도면/DB를 사용할 수 있는 것은 별개다.

## 반드시 저장해야 할 데이터

1. 건물: ID, 공식명·별칭·구 명칭, 건물번호, 외곽/대표 좌표, 실제 출입구, 공개 가능한 설명·사진, 운영시간/개방 조건.
2. 층: 건물 ID, 실제 층 식별자(B1/1F 등), 도면 이미지/SVG와 버전, 도면 폭·높이·방향·축척 또는 기준점. 지도 좌표와 도면 좌표는 별도로 관리.
3. 강의실/시설: ID, 이름·별칭·종류, 건물·층·호실, 도면 위 위치(x/y), 접근할 문/복도 노드, 사용 조건·운영시간·유료 여부·확인일·출처·공개 상태.
4. 보행망: 출입구·복도 분기·방 문·계단·엘리베이터를 노드로, 실제 걸을 수 있는 구간을 선으로 연결. 구간 길이·방향·층 이동·계단·운영시간·폐쇄 여부·추정/실측 소요 시간을 기록.
5. 실외 접점: 외부 지도 경로 끝과 자체 보행망이 실제 만나는 출입 지점. 건물 중심으로 선을 긋는 것으로 대체하지 않음.

평면도 이미지만으로 화살표 길찾기가 완성되지는 않는다. 이미지 위에 보행 가능한 선과 문 위치를 등록하고, 탐색 결과를 해당 층 도면 좌표에 화살표로 그린다. 엘리베이터/계단을 누르면 다음 층 도면으로 이어진다. 실내 GPS 층 추적은 별도 문제이므로 초기에는 사용자 단계 확인을 사용한다.

## UI 적용 방안

- 검색창 아래 가로 스크롤 범주 칩: 카페/식당/편의점/자판기/정수기/라운지/ATM/스터디룸/흡연부스/쓰레기통. 선택한 범주의 목록·마커·숫자를 함께 갱신.
- 화면 픽셀상 가까운 시설을 묶고 동일 아이콘 우측 상단에 개수 표시. 확대 후에도 가까우면 묶음을 유지. 동일 좌표의 다른 층 시설은 최대 확대에도 분리되지 않으므로 숫자를 누르면 층/시설 목록을 제공.
- 현재 지도 구현은 CustomOverlay 중심이다. 카카오 MarkerClusterer를 쓸 경우 표준 Marker/스타일로 맞추거나 별도 픽셀 군집 처리 필요. 라이브러리를 추가하는 것만으로 기존 핀에 자동 적용되지는 않음.
- 건물 핀 토글은 시설 범주 표시와 구분한다. 건물 카드: 정보, 건물 개방 시간, 보유 시설, 층별 내부 지도, 출발/도착. 매장 영업시간과 건물 출입시간은 분리.
- 메인 검색은 '교내 우선'을 기본으로 하고 '학교 주변/외부 검색'을 명시적으로 전환할 수 있게 한다. 실외 연계를 유지하려면 길찾기 출발지에서 외부 주소·역·정류장을 계속 검색할 수 있어야 함.
- 교내 시설 검색은 공급자 결과 없음과 무관하게 자체 DB에서 수행. 건물명·별칭·호실을 조합해 검색하고 동일 호실 번호를 건물별로 구별.

[카카오 군집 기능 문서](https://apis.map.kakao.com/web/documentation/#MarkerClusterer)는 픽셀 격자 크기·확대 레벨·최소 마커 수·표시 스타일 설정을 제공한다. 같은 위치의 다층 시설 구별은 앱에서 추가 구현한다.

## 등록·유지보수 방식

공개 자료 가져오기 → 관리자 검토 → 현장 보정 → 공개 순서로 운영한다. 시설은 지도/도면에서 클릭하고 입력하며 CSV 일괄 등록을 제공한다. 원본 자료의 출처·사용 범위·확인일을 보관하고, 제보는 즉시 공개하지 않고 승인한다. 폐쇄·이동·고장·방학 운영 변경을 수정할 수 있어야 한다. OCR/AI는 도면 글자·시설 목록의 초안 추출에 활용할 수 있지만 문·복도 연결과 통행 가능 여부를 검증한 것으로 취급하지 않는다.

건물 카드의 보유 시설은 시설 레코드에서 집계한다. 별도 수기 목록을 중복 관리하지 않는다. 시설 추가와 경로 연결을 분리하여 '지도 표시 가능/길찾기 가능/미검증' 상태를 구별한다.

## 첫 범위와 준비물

학교 전체를 한 번에 등록하기보다 IT1 306호까지를 먼저 완성하고 IT1→2·5호관 연결로 확장한다.

- IT1 진입 층과 306호가 있는 실제 층의 최신 도면 또는 현장 안내도.
- 306호 문, 복도 분기, 엘리베이터·계단, 3층 서편 출입구의 위치.
- 서편 출입구 이후 2·5호관 각각의 실제 도착 층/출입구·방향·개방 조건.
- 해당 층의 실제 편의시설 몇 곳과 위치·이용 조건.
- 현장 보행/층 이동 시간 측정과 갱신 담당자.
- 도면 제공·가공·서비스 게시 가능 범위 확인.

1차 완료 조건: 외부 출발지 검색 → IT1 306호 검색/시간표 지정 → 실제 출입구까지 외부 경로 → 층별 도면 화살표 → 강의실 문까지 안내 → 전체 이동 시간/출발 시각 일치. 미확인 연결을 임의로 채우지 않는다.

## 브랜치·테스트 배포 평가

사용자 제안은 적절하다. 다만 사이트만 나누고 DB/키/출처 허용 설정을 공유하면 격리가 완성되지 않으므로 아래 보완 후 실행을 권장한다.

| 용도 | Git 브랜치 제안 | Vercel | 데이터 |
| --- | --- | --- | --- |
| 운영 | main | 기존 knu-campus-navigation | 운영 DB/Auth/Storage |
| 통합 테스트 | staging | 신규 knu-campus-navigation-test(이름·주소 미확정) | 독립 테스트 DB/Auth/Storage, 테스트 계정 |
| 기능 개발 | codex/feature-campus-local-navigation 등 | 기능별 Preview, 필요 시 | 테스트 데이터만 사용 |

별도 프로젝트가 테스트용이라도 그 프로젝트에서 staging을 Production Branch로 지정하면 테스트 고정 주소 배포는 그 프로젝트의 Production 환경변수를 사용한다. 기존 운영 프로젝트의 Production 환경변수를 복제해 두지 않는다. Vercel의 일반 비운영 브랜치 Preview를 이용하면 별도 프로젝트 없이도 시험 가능하지만, 사용자처럼 고정 테스트 사이트를 원하는 경우 별도 프로젝트 방식도 타당하다.

개발 흐름: 운영 main에서 기능 브랜치 → 기능 PR/검사 → staging 통합/테스트 주소 확인 → 선택된 기능만 main 대상 PR → 운영 배포 후 검증. staging의 미완성 기능 전체를 운영으로 한꺼번에 합치지 않는다. main 재빌드 시 운영 환경변수 차이를 다시 검증한다. 테스트 프로젝트 URL을 운영 URL에 단순 덮어씌우는 방식은 사용하지 않는다.

실행 전 보완 사항:

- 테스트 DB/Auth/Storage 분리, 익명화된 샘플 데이터 사용. 테스트 중 운영 시간표·사용자 정보 복사/수정 금지.
- 운영자 시설 편집 권한과 일반 공개 읽기 권한 분리. 테스트용 공개 계정이 운영 관리자 권한을 갖지 않게 함.
- 카카오 JS 허용 도메인, 인증 반환 주소, 서버 허용 출처에 확정된 테스트 주소만 추가. 현재 server/vercel-handler.cjs에는 운영 주소 등 고정 허용 출처가 있으므로 단순 복제 시 테스트 요청이 실패할 수 있음. 모든 출처 허용으로 해결하지 않음.
- 테스트 외부 API 키·사용량/비용, 배포 접근 제한 적용 가능 범위, 검색 노출 방지 확인. 실제 GPS/도보는 테스트 주소의 휴대폰 브라우저에서도 점검.
- 검증: 기존 시간표/학식/실외 경로 회귀 검사, 교내 별칭/호실 검색, 층간 연결, 닫힌 문/운영시간, 군집 개수, 손잡이 패널, 실외+실내 시간 중복 가산 여부, 본인 데이터 접근, 빠른 선택 변경에 따른 오래된 응답 무시.
- DB 변경은 이행 파일로 버전 관리하고 테스트부터 적용. 코드 롤백과 시설 데이터/DB 롤백은 별도 계획. 운영 시설 데이터는 검토한 레코드/버전만 승격.

[Vercel Git 연동](https://vercel.com/docs/git), [환경 구분](https://vercel.com/docs/deployments/environments) 참조. 이번에 계정에서 목록 조회한 knu 검색 결과에는 운영 크누패스와 학식 프로젝트만 나타났다. 크누패스 배포 상세 조회는 팀 권한 오류(403)로 실패했다. 따라서 실제 Production Branch·환경변수·보호 설정은 아직 확인되지 않았고 재인증 후 확인이 필요하다. 권한 변경이나 인증 절차는 시작하지 않았다.

## 이번 작업 상태

관련 코드/프로젝트 규칙 확인과 공개 자료 조사, 본 검토 문서 작성만 수행했다. 기능 구현 테스트·빌드·새 브랜치 생성·Vercel 테스트 프로젝트 생성·DB 생성·설정 변경·배포는 수행하지 않았다. 기존 미커밋 설계 문서는 보존했다. 이후 실행 여부가 확정되면 비용·권한·정확한 주소/환경을 확인한 뒤 준비 작업을 진행한다.
